# 04.3 工具说明

版本：Pi **v1.0.0**（`a13d35a74`） · 记录日期：2026-10-25

所属模块：[04 消息历史与上下文准备](04-消息历史与上下文准备.md)。工具说明让模型知道有哪些能力、何时使用以及如何传参；真实操作仍由宿主程序执行。

## 1. 工具说明包含什么

以 [read 工具](../../pi/packages/coding-agent/src/core/tools/read.ts) 为例：

| 字段 | 作用 |
| --- | --- |
| `name` | 调用名称，如 `read` |
| `description` | 描述能力、限制与使用方式，如支持文本和图片、大文件输出会截断 |
| `parameters` | 用 JSON Schema 规定参数结构，`read` 要求 `path`，可选 `offset`、`limit` |
| `promptSnippet`、`promptGuidelines` | 为系统指令贡献简短用途说明和使用规则 |
| `execute()` | 宿主中的执行函数，不发送给模型 |

JSON Schema 是描述数据结构的规则，例如规定字段类型和必填项。模型据此生成工具参数，运行时也会在执行前校验参数。

## 2. 自然语言摘要与结构化声明

工具说明有两个配合使用的层次：

- **系统指令中的摘要与规则**：帮助模型判断何时使用工具，例如“用 read 查看文件”。
- **结构化工具声明**：提供准确的调用名称、描述与参数结构。

仅在提示词中写“你能读取文件”，不会自动注册一个可执行工具。

下面是精简后的 `read` 声明示意，省略可选参数与其他声明配置，描述也作了简化：

```json
{
  "name": "read",
  "description": "读取文件内容",
  "parameters": {
    "type": "object",
    "properties": { "path": { "type": "string" } },
    "required": ["path"]
  }
}
```

声明告诉模型如何生成 `read({"path":"README.md"})` 这样的调用，不包含文件内容。

## 3. Pi 如何准备工具声明

```text
已注册的工具定义
  → 会话选择本次启用的工具
  → AgentContext.tools（含 execute 等宿主能力）
  → toToolDeclaration() 提取可发送的声明
  → 与历史中的工具状态比较
  → 通过 system 消息记录 toolsAdded / toolsRemoved
```

[declareToolChanges()](../../pi/packages/agent/src/agent-loop.ts) 对比当前可执行工具集合与消息中已经声明的工具状态。

| 情况 | 消息中的变化 |
| --- | --- |
| 新增工具 | 在 `toolsAdded` 中记录完整声明 |
| 移除工具 | 在 `toolsRemoved` 中记录工具名称 |
| 同名工具的声明发生变化 | 先移除旧声明，再加入新声明 |
| 声明没有变化 | 不重复追加工具变化 |

[getCurrentTools()](../../pi/packages/ai/src/utils/transcript.ts) 按消息顺序重放这些变化，得到当前工具声明。模型适配器再将声明转换成对应提供商的请求格式；`toolsAdded` 是 Pi 内部的消息字段，不表示所有模型 API 都接受同名字段。

`toToolDeclaration()` 只保留名称、描述、参数结构和可选的采样约束，不保留 `execute`、界面标签等宿主字段。工具声明与真正可执行的工具需要对应，模型才不会收到一个运行时找不到的工具名。

## 4. 声明之后发生什么

模型返回工具名称和参数后，主循环查找本地工具、校验参数，再调用 `execute()`。执行结果作为 `toolResult` 消息进入下一次请求；完整闭环见 [第 03 篇](03-Agent基础与最小运行闭环.md)。

工具参数校验确认的是数据结构，不等于执行成功；文件不存在等问题仍需由实际工具处理。
