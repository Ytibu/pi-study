## 2. 先理解启动什么

这是一个使用 npm workspaces 管理多个包的仓库。根目录不是带有 `npm run dev` 的网页应用；根 `package.json` 没有 `start` 或 `dev` 脚本。

| 位置 | 职责 | 与当前启动的关系 |
| --- | --- | --- |
| `packages/coding-agent` | CLI、交互模式、print/JSON/RPC、工具和会话管理 | 本次启动入口 |
| `packages/agent` | 代理循环、工具调用及状态管理 | CLI 下层运行时 |
| `packages/ai` | 模型目录、认证、不同模型服务的 API 适配 | 启动需加载模型元数据；对话需认证 |
| `packages/tui` | 终端界面、键盘输入、原生平台能力 | 交互界面依赖；仓库已带 Windows 原生预编译文件 |
| `packages/chord`、`telemetry`、`codemode`、`mcp` | 应用组合、遥测、脚本工具及 MCP 支持 | 依赖由根目录统一安装 |
| `packages/durable`、`protocol`、`client`、`server` | 持久化与客户端/服务端相关能力 | 暂不作为入门启动目标 |
| `packages/evals` | 评估工具 | 不需要先运行评估才能启动 CLI |

普通 CLI 源码启动不需要先启动数据库、Redis、网页开发服务器，也不需要先构建独立二进制。模型服务可以是远端提供商或另行配置的本地模型。

注意根包版本为 `0.0.3`，`coding-agent` 等工作区包版本为 `1.0.0`。判断当前学习版本应结合 Git 标签和 CLI `--version`，不要只看根包版本。

## 3. Windows 源码启动步骤

### 3.1 检查现有环境

以下命令在 PowerShell 中执行：

```powershell
Set-Location E:\codeSpace\openCode\pi
git describe --tags --always
git status --short
node --version
npm --version
git --version
Get-Command node,npm,git,bash,pwsh -ErrorAction SilentlyContinue
```

需要 Node.js `22.19.0` 或更新版本、npm 和可用于工具命令的 Shell。本机已有 Node.js、PowerShell 7、Git Bash 和 WSL Bash，本次没有重复安装工具链。

### 3.2 安装依赖

首次克隆、依赖目录尚不存在时，在根目录执行：

```powershell
npm ci --ignore-scripts
```

`npm ci` 按现有 `package-lock.json` 安装；它会重建依赖目录，不适合在其他进程正在使用依赖时反复执行。仓库 README 也提供 `npm install --ignore-scripts`，适用于日常补装依赖；本次选择锁文件安装以减少版本漂移。

`--ignore-scripts` 来自仓库开发规则，用于禁用依赖生命周期脚本。普通源码启动不需要为此手动执行所有依赖的安装脚本。本次安装成功输出 `added 319 packages in 2m`，未修改锁文件。

### 3.3 补齐模型 JSON 数据

```powershell
npm run hydrate:model-data
npm run check:model-data
```

预期校验结果：

```text
Generated model data is valid.
```

`packages/ai/src/providers/data/` 被 `.gitignore` 忽略，单纯克隆 Git 仓库不会获得其中的 JSON。各提供商的 `*.models.ts` 和 `providers/all.ts` 会导入这些文件，因此不能把“依赖安装完”视为源码运行的全部准备工作。

`hydrate:model-data` 执行 `generate-models.ts --strict --data-only`，获取模型目录并写入被忽略的数据文件，不改写生成的 TypeScript 目录文件。本次完成后，检查确认 `models.generated.ts`、提供商源码和锁文件均无差异。

这一步会访问 models.dev、NVIDIA NIM、OpenRouter、Vercel AI Gateway、Radius 等模型目录接口，需要网络，但没有发送模型推理请求。本次完成输出：

```text
Hydrated JSON model values under src/providers/data/
```

模型元数据取自执行时的目录，**不是 v1.0.0 发布当日的冻结快照**。本次统计有 1597 个 tool-capable 模型，仅作为执行记录，后续不应以该数字作为成功条件。若需要严格复现发布时的模型数据，可研究根 README 中带模型数据的 release source archive；本次没有下载或验证该路径。

### 3.4 验证源码入口

```powershell
pwsh -NoProfile -File .\pi-test.ps1 --version
pwsh -NoProfile -File .\pi-test.ps1 --help --offline --no-approve --no-extensions
```

本次分别返回 `1.0.0` 和完整帮助，退出码均为 `0`。帮助验证使用的额外参数用于关闭自动联网、跳过项目资源信任及扩展发现，缩小基础检查范围。

也可以使用现有终端直接执行：

```powershell
.\pi-test.ps1 --version
```

CMD 包装入口也已验证：

```bat
pi-test.bat --version
```

它调用 Windows PowerShell，传入 `-NoProfile -ExecutionPolicy Bypass` 后运行同一个 `.ps1`。本次没有发生执行策略报错；若直接执行 `.ps1` 被本机策略阻止，可先使用此包装入口。组织策略仍可能优先，不要据此修改全局执行策略。

### 3.5 打开交互模式，完成认证

以下为待手动完成的操作：在真实终端运行，**不要将输出重定向到文件或管道**。

```powershell
Set-Location E:\codeSpace\openCode\pi
pwsh -NoProfile -File .\pi-test.ps1
```

进入界面后：

```text
/login
/model
```

`/login` 选择提供商并按提示使用 API Key 或 OAuth；`/model` 选择可用模型。具体支持方式以本版本 [`providers.md`](../../packages/coding-agent/docs/providers.md) 为准。

随后输入一个简单问题并等待完整回复。需要验证命令工具时，可在编辑器输入：

```text
!printf 'Bash is working\n'
```

编辑器为空时按 `Ctrl+D` 退出；默认 `Ctrl+C` 第一次清空编辑器、第二次退出。键位可配置，见上游 [`keybindings.md`](../../packages/coding-agent/docs/keybindings.md)。

交互模式依赖 stdin 和 stdout 都是真实终端。重定向其中一个流时，程序会选择 print 模式；因此不能通过捕获普通命令输出证明交互界面渲染成功。

## 4. 配置和其他运行方式

### 4.1 配置存放位置

默认用户目录为 `~/.pi/agent/`，Windows 中对应 `$HOME\.pi\agent`：

| 路径 | 用途 |
| --- | --- |
| `settings.json` | Shell 路径、默认模型、工具及界面设置 |
| `auth.json` | API Key、OAuth 等认证信息 |
| `models.json` | 自定义模型服务地址和模型覆盖 |
| `sessions/` | 持久化会话 |
| 项目 `.pi/` | 项目设置、扩展、技能和提示模板 |

`PI_CODING_AGENT_DIR` 可以切换用户配置目录。本次后续 CLI/RPC 验证使用 `.artifacts/startup-study/` 下的隔离目录，避免混用已有用户认证。

项目 `.pi/` 中的配置和资源受项目信任控制；首次交互启动可能显示信任提示。按提示阅读后选择。`--no-approve` 只在当前进程忽略这些项目资源，适合定位基础启动问题；`AGENTS.md` 等上下文文件发现另受 `--no-context-files` 控制。

### 4.2 从其他工作目录启动

脚本文件所在位置决定从哪里加载 Pi，调用者当前目录决定 Pi 工作在哪个项目。脚本不会自动切换到仓库根目录。

例如先切换到需要学习或操作的项目目录，再调用：

```powershell
& E:\codeSpace\openCode\pi\pi-test.ps1
```

本次从 `packages/` 目录使用绝对脚本路径运行 `--version`，返回 `1.0.0`。工作目录保留行为还由启动脚本源码确认。

### 4.3 一次性文本、JSON 和 RPC

```powershell
# 需要先配置认证；本次没有执行成功的模型对话
.\pi-test.ps1 --print "简要解释这个项目的用途"
.\pi-test.ps1 --mode json "简要解释这个项目的用途"

# 等待外部程序通过 stdin 发送 JSONL 命令
.\pi-test.ps1 --mode rpc --no-session --model openai/gpt-4o-mini
```

JSONL 指每行一个 JSON 对象。RPC 允许客户端读取状态、执行工具和提交提示；本次只测试了不调用模型的状态读取与 Bash 命令。上面的模型 ID 是本次 RPC 实测选择值，不代表已验证其在线可用性。

`--no-session` 禁止持久化会话，仍可能使用或创建配置文件。`--offline` 禁止自动网络活动，不会提供模型凭据，也不是把远端模型变成本地模型的开关。

### 4.4 发布包安装与源码运行的区别

学习当前克隆代码优先使用源码脚本。若只需要已发布 CLI，上游提供 npm 全局安装；固定学习版本的命令为：

```powershell
npm install -g --ignore-scripts @earendil-works/pi-coding-agent@1.0.0
pi --version
```

本次没有执行全局安装。发布包的 `pi` 指向包内 `dist/bundle/cli.js`，并不运行当前工作区源码。

Linux/macOS 的源码入口为 `./pi-test.sh`，本次未在这些系统实测。v1.0.0 中该脚本加载 `src/experimental/cli.ts`，Windows 脚本加载 `src/cli.ts`；实验入口会先处理实验命令，再转入普通 `main()`，不要假定三个包装脚本逐字等价。

## 5. 启动链路与源码阅读入口

Windows 的基础调用路径：

```text
pi-test.ps1
  -> node --import <source-resolver.ts 的 file URL> src/cli.ts
  -> source-resolver.ts 读取根 tsconfig.json 的 paths，注册工作区源码解析
  -> cli.ts 调用 setupCli() 和 main(args)
  -> main.ts 处理参数、配置、会话、项目资源信任、模型和工具
  -> 按终端条件及参数选择 InteractiveMode / runPrintMode / runRpcMode
```

Node.js 原生处理可擦除的 TypeScript 语法，但不会自动应用 TypeScript `paths` 别名。解析器把 `@earendil-works/*` 导入映射到工作区 `src`，所以源码启动不必先生成所有包的 `dist`。

`--version` 在参数解析后提前退出；`--help` 则会经过更多运行时初始化以收集扩展参数。因此版本成功、帮助成功、会话成功和真实模型回复是不同层级的证据。

| 入口 | 阅读目的 |
| --- | --- |
| [`package.json`](../../package.json) | workspaces、环境要求和根命令；不存在常规 dev/start 脚本 |
| [`pi-test.ps1`](../../pi-test.ps1)、[`pi-test.bat`](../../pi-test.bat)、[`pi-test.sh`](../../pi-test.sh) | 平台包装、参数转发与入口差异 |
| [`source-resolver.ts`](../../packages/coding-agent/src/experimental/source-resolver.ts)、[`tsconfig.json`](../../tsconfig.json) | 工作区源码别名解析 |
| [`cli.ts`](../../packages/coding-agent/src/cli.ts)、[`setup.ts`](../../packages/coding-agent/src/cli/setup.ts)、[`main.ts`](../../packages/coding-agent/src/main.ts) | CLI 初始化、参数分流和运行时创建 |
| [`config.ts`](../../packages/coding-agent/src/config.ts) | 版本、资源及用户配置目录 |

## 6. 本次问题与处理记录

### P01：npm 安装因缓存限制失败

- **现象**：首次 `npm ci --ignore-scripts` 退出码 `1`，出现 `ENOTCACHED` 和 `cache mode is 'only-if-cached'`。缺失包示例为 `@anthropic-ai/sdk` 的传递依赖版本 `0.52.0`，不要与工作区直接依赖版本混淆。
- **原因**：首次命令执行环境限制联网，实际只能读缓存；缺失包没有命中缓存。
- **处理**：允许该安装命令联网后，原命令重试成功。未修改 registry、锁文件或依赖版本。
- **复习**：普通终端遇到同类错误，先检查 `npm config get offline` 和命令环境的联网限制。仅当自己的 npm 确实被设为离线时，可对单次安装使用 `npm ci --ignore-scripts --offline=false`；该变体未在本次执行。

首次失败还出现依赖目录清理 `EPERM` 和 npm 缓存日志目录不可写。重试后安装成功，没有手动删除整个工作区或修改文件系统权限。若普通终端仍出现 `EPERM`，再检查占用该依赖目录的具体进程。

### P02：npm 配置与依赖警告

| 输出 | 分析与本次处理 |
| --- | --- |
| `Unknown project config "min-release-age"`；子命令中的 `Unknown env config` | 仓库 `.npmrc` 声明 `min-release-age=2`，本机 npm 11.6.2 不识别。安装继续成功，但不能声称该保护已生效；本次保留上游配置 |
| `EBADENGINE`，`autoevals@0.3.0` 要求 `please-use-pnpm` / `pnpm >=10.27.0` | 来自 `packages/evals` 的开发依赖，反映该依赖的包管理器声明；不是 Pi 的 Node 最低版本检查失败。根仓库明确使用 npm，本次没有切换包管理器，CLI/RPC 检查通过；评估功能未验证 |
| `prebuild-install@7.1.3` deprecated | 依赖维护状态警告；没有阻断安装，本次未更新依赖 |
| `node-domexception@1.0.0` deprecated | 建议使用平台原生 DOMException 的依赖警告；没有阻断安装，本次未更新依赖 |

以上警告仍然存在，不写成“全部消除”。本次范围是运行 v1.0.0 并记录现象，不是升级依赖。

### P03：Git 克隆不包含模型 JSON

- **发现**：安装过程中检查到 `packages/ai/src/providers/data/` 不存在，且其路径被 Git 忽略。源码存在对 JSON 和 `.manifest.json` 的静态导入。
- **处理**：在启动验证前执行 `npm run hydrate:model-data`，随后 `npm run check:model-data` 通过。
- **结果**：源码 `--version`、`--help`、RPC 均通过，生成的 TypeScript 和锁文件无改动。
- **边界**：本次是在启动前预先补齐，未实际触发“缺失模型 JSON”的启动异常。后续若目录丢失或校验提示 stale/missing，优先重复补齐与校验；不要手写 JSON 或直接编辑 `models.generated.ts`。

### P04：直接运行 cli.ts 找不到 dist/index.js

实际执行：

```powershell
node packages/coding-agent/src/cli.ts --version
```

结果退出码 `1`：

```text
Error [ERR_MODULE_NOT_FOUND]: Cannot find module
...node_modules\@earendil-works\pi-ai\dist\index.js
```

原因是绕过了源码解析器，Node 按包的发布入口寻找尚未构建的 `dist`。改用 `pi-test.ps1` 或 `.bat` 后返回 `1.0.0`。源码学习不需要用全量构建来绕过这个问题。

### P05：Windows 自动选择了 WSL Bash

源码查找顺序：`settings.json` 的 `shellPath` → `Program Files` / `Program Files (x86)` 下的 Git Bash → PATH 上的 `bash.exe`。

本机 Git 在 D 盘，默认常见目录检查未找到它，最终选择 `C:\Windows\System32\bash.exe`，参数为 `-s`、从 stdin 接收命令。**本次默认 WSL Bash 实测 `printf` 成功，退出码 `0`，并非启动故障。**

为了确认能明确选择 Windows Git Bash，本次在隔离配置中写入：

```json
{
  "shellPath": "D:\\Program Files\\Git\\bin\\bash.exe"
}
```

随后通过 Pi RPC 的 `bash` 命令执行 `printf "Bash is working\n"`，返回 `exitCode: 0` 和预期文本。若希望日常使用同一路径，可将该字段合并到自己的 `settings.json`，保留其他已有设置；本次没有修改用户默认配置。

### P06：执行环境拒绝创建子进程

- **现象**：本次临时验证脚本内 `spawnSync node.exe` 返回 `EPERM`。在受限环境直接检查 Bash 时，还出现 `couldn't create signal pipe, Win32 error 5` 和 WSL `E_ACCESSDENIED`。
- **处理**：在允许本地子进程的执行环境重跑，CLI、WSL Bash 及 Git Bash RPC 均通过。
- **判断**：这是本次自动化执行环境的限制，不能直接判为 Pi 程序缺陷，也不应据此要求普通用户用管理员权限运行 Pi。

### P07：有模型目录，但没有认证，仍无法对话

本次隔离配置及提供商凭据环境变量后验证：

| 检查 | 结果 | 含义 |
| --- | --- | --- |
| `--list-models` | `No models available`，退出码 `0` | 列出的是当前可用模型；有元数据不等于有凭据 |
| `--print hello` | `No API key found for the selected model`，退出码 `1` | 已进入运行路径，但没有完成模型调用 |
| `auth check --provider openai --json --no-refresh` | `status: not_ready`，`reason: credentials_not_configured`，退出码 `1` | 认证尚未配置；不是远端鉴权成功或失败的证明 |

后续通过交互 `/login` 配置凭据，再 `/model` 选择模型并发送简单问题。认证检测建议使用 `auth check`；不要把 `auth print-api-key` 或带 `--credentials` 的输出写入学习文档。

脚本中的 `--no-env` 只清理脚本列举的一部分变量，既不清空 `auth.json`，也没有覆盖提供商文档中的所有变量；不能单靠它证明完全无认证。本次使用单独配置目录和只保留必要系统变量的子进程环境完成无凭据验证。

### P08：交互测试工具不可用

仓库要求交互模式测试遵循 [`.pi/skills/interactive-testing.md`](../../.pi/skills/interactive-testing.md)，使用受控 tmux 终端。Windows PATH、Git Bash 和 WSL 中均未找到可用 tmux；后两者在允许子进程的环境中检查，查找退出码均为 `1`。

本次没有额外安装 tmux，也未把非交互输出冒充 TUI 验证。后续在本机真实终端按第 3.5 节手动检查；若要做仓库规范的自动化交互测试，再准备 tmux 环境并遵循原测试说明。
